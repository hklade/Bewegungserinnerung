# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Bewegungserinnerung ("movement reminder") is a local React/Vite prototype: an hourly movement/break reminder app with activity logging, a hydration ("Trinkmanager") tracker, day/week evaluation views, and CSV import/export. UI text and domain terms are in German.

## Commands

```bash
npm run dev              # Vite dev server (proxies /api to the Node server on :3001)
npm run build             # production build
npm run preview           # preview a production build

npm run test:server       # run server unit tests (node --test tests/server/*.test.mjs)
npm run test:e2e          # Playwright e2e tests + Allure report generation
npm run test:e2e:plain    # Playwright e2e tests only, no Allure
npm run test:e2e:headed   # Playwright e2e tests, headed browser
```

Run a single server test file directly: `node --test tests/server/hydration-timestamp.test.mjs`.

Run a single Playwright test: `npx playwright test tests/hydration.e2e.spec.ts` (add `-g "test name"` to filter by title).

The frontend server (Vite) and the API server (`server.mjs`, listening on `127.0.0.1:3001`) are separate processes — `npm run dev` only starts Vite. Playwright's global setup/teardown (`tests/helpers/global-setup.ts` / `global-teardown.ts`) manages starting the API server for e2e runs.

## Architecture

**Two runtimes in one repo:**
- `src/` — the React/TypeScript frontend; no router or component library. `App.tsx` is a thin composition root over feature-scoped hooks (`src/hooks/`) and presentational components (`src/components/`), with types (`src/types.ts`), constants (`src/constants.ts`), pure helpers (`src/lib/`), and the API client (`src/api/dashboardApi.ts`) split out.
- `server/` — a plain Node.js `http` server (no framework) that owns all persistence and business logic, imported by `server.mjs`.

**Server module layering** (`server/`):
- `http.mjs` — the only place that defines routes (`/api/config`, `/api/dashboard`, `/api/bookings`, `/api/bookings/import`, `/api/bookings/export`, etc.) and handles request/response plumbing (JSON/text body parsing, CORS headers).
- `service.mjs` — business logic: builds the dashboard payload (today stats, current week, recent weeks, heatmap), generates automatic "missed reminder"/"unanswered" backfill entries, and handles booking creation/import/replace.
- `storage.mjs` — reads/writes/normalizes the CSV-backed entry storage (movement entries and hydration entries each have their own CSV schema and file).
- `config.mjs` — loads/saves JSON config (reminder times, weekday-only flag, export path, hydration goal), computes reminder time slots from start/end times, and resolves file paths. Switches between default and `test`-suffixed config/data files based on `NODE_ENV=test`.
- `utils/time.mjs`, `utils/parsing.mjs` — timezone-aware (Vienna) date/time helpers and CSV/number/boolean parsing helpers shared across the server modules.

**Data model:** All persisted data is CSV, not a database (see the removed-DB commit in git history). There are two parallel CSV files per environment: one for movement entries (`Bewegungsdaten.csv` / `Test-Bewegungsdaten.csv`) and one for hydration entries (`Trinkdaten.csv` / `Test-Trinkdaten.csv`), located under `data/`. The configured `exportPath` in `config/*.config.json` points at the movement CSV; hydration path is derived separately in `config.mjs`.

**Reminder scheduling logic** lives in one shared module, `shared/reminder-schedule.mjs` (plain ESM, no TypeScript-only syntax, so it can be imported unchanged by both a Vite/TypeScript client bundle and a plain Node ESM server): time parsing/formatting (`normalizeTime`, `parseTimeToMinutes`, `formatMinutesToTime`), hourly slot computation from start/end times (`buildReminderSlots`, `buildReminderSlotsFromStart`), and weekdays-only eligibility (`isWeekdayEligible`). `server/config.mjs`/`server/utils/time.mjs` and `src/App.tsx` (client-side countdown/popup display) both import from it rather than each keeping their own implementation.

**Test layout:**
- `tests/server/*.test.mjs` — Node's built-in test runner against server modules directly (config loading, hydration timestamp logic, server smoke test).
- `tests/*.e2e.spec.ts` — Playwright end-to-end specs driving the full app through a browser; helpers live in `tests/helpers/` (fixtures for config, file helpers, logger, Playwright helper, global setup/teardown that starts/stops the API server against the `test` config).
- Playwright is configured for **serial execution** (`fullyParallel: false`, `workers: 1`) specifically to avoid races over the shared test config/CSV files.
- Allure results/report output to `allure-results/` / `allure-report/` (gitignored, generated by `test:e2e`).

## Notes

- `vite.config.ts`'s `build.outDir` and the default `exportPath` in `config/bewegungserinnerung.config.json` point at Windows user-specific paths (`C:\Users\HeidiKlade\...`) — this repo is developed across both a Windows host and a Linux devcontainer, so don't be surprised by mixed path conventions; check which environment you're in before assuming a path is wrong. Running `npm run build` in the Linux devcontainer creates a literal `C:/` directory under the repo root as a side effect (Vite doesn't recognize the Windows path and treats it as relative); this is a build artifact, not tracked or required — safe to `rm -rf "C:/"` after a local build.
- `package.json` declares both `@rollup/rollup-linux-x64-gnu` and `@rollup/rollup-win32-x64-gnu` as explicit `optionalDependencies` so `npm install` fetches the native Rollup binary for both platforms regardless of which one it's run from. Without this, `node_modules` populated on one platform silently lacks the binary the other needs, and `npm run dev`/`npm run build` fail with `Cannot find module @rollup/rollup-<platform>` on the other platform until `npm install` runs there too. If a new native optional dependency shows the same single-platform-only failure, the fix is the same: pin both platforms' packages explicitly rather than relying on npm's per-platform default resolution.
- `NODE_ENV=test` is the switch that redirects both config and data files to their `Test-`-prefixed counterparts, keeping e2e/unit test runs from touching real user data. `server.mjs` normalizes an absent/unrecognized `NODE_ENV` to `production` at the top of the file (before importing `server/config.mjs`) and `server/http.mjs`'s `startServer()` logs the active environment and resolved file paths on every boot — check that log line first when data ends up in the wrong file. Repeated local `npm run test:e2e`/`test:e2e:plain` runs still accumulate duplicate smoke-test entries (e.g. `pom-smoke-test`) in the `Test-`-prefixed CSVs across runs (this is about test-data hygiene between runs, not prod/test isolation) — treat `data/Test-*.csv` as needing a reset between exploratory e2e runs if a test asserts on exact row counts/uniqueness.
- The `NODE_ENV` switch only prevents *startup* from picking the wrong file — it does not make every code path immune to writing to the wrong file. `server/config.mjs`'s config-path resolution used to fall back unconditionally to the production export path whenever a caller (e.g. a `PUT /api/config` payload, or a test's cleanup hook) omitted `exportPath`, regardless of the active `NODE_ENV` — letting an otherwise-correctly-`NODE_ENV=test`-started server get silently redirected into writing the real production CSV. When adding a new "resolve environment-dependent path/value from an optional override" helper anywhere in `server/`, make the fallback branch on the *current* environment, not on a fixed default — the fixed-default version looks correct in isolation but reintroduces exactly the isolation gap `NODE_ENV=test` is supposed to close.
- This devcontainer can have multiple independent Claude Code sessions open on the same workspace at once (visible via the agent-listing tool). They share the same filesystem, the same fixed ports (`3001` for the API server, Vite's default frontend ports), and the same `data/*.csv` files. If a CSV or config file changes in a way you didn't cause, check for other active sessions before assuming your own code has a bug — a `git status`/`stat`-timestamp mismatch against what you just ran is the first sign.
- `tsconfig.json` sets `moduleResolution`/`module: "nodenext"`, which requires explicit `.js` extensions on relative imports between TypeScript files (e.g. `import { x } from "./foo.js"` even though the source file is `foo.ts`) — this is TS's documented nodenext convention (the extension names the emitted JS, not the source). `npm run build` (Vite/esbuild) does not enforce this and will build fine without it, so a missing extension is invisible until something runs `tsc --noEmit` directly. When adding new `src/` modules with relative imports, include the extension up front rather than relying on the build to catch it.
